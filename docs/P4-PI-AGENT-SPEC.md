# P4 控制面板 ↔ 树莓派 Agent 接入规格书（给 OpenClaw 的实现依据）

> **给 OpenClaw 的话**：本文是**契约文档**，不是实现代码。文档作者（Claude Code）在 Windows 上
> 负责 ESP32-P4 固件侧，看不到树莓派的实际环境，因此**刻意不提供完整代码**，也不假设你的
> 进程模型、语言、依赖管理方式。
>
> **你拥有完全的实现自主权**：Python 版本、包管理（apt / pip / venv / pipx）、MQTT 客户端库、
> Agent 调用方式、进程守护（systemd / supervisor / screen）、目录结构、日志方案 —— 全部由你
> 按树莓派的实际情况决定，不必请示。
>
> **唯一不可改动的是第 4 节和第 5 节的 MQTT 契约**：主题名、JSON 字段名、数据类型、`seq` 语义、
> `final` 语义。P4 固件会按它写死解析，任何漂移都会直接表现为"屏幕上一直转圈"或"回执串行错乱"，
> 而且排查要跨两台设备、两种语言，成本极高。
>
> **遇到契约本身有问题时**（某个字段拿不到、某个设计在你这边不合理），**不要自行变更**，
> 先把问题报告给用户，由用户转达给固件侧修订。宁可停下来问，也不要让两侧的假设悄悄分叉。
>
> **第 7 节的自验是硬性分界线**：在它通过之前，P4 固件的 MQTT 部分**一行都还没写**，
> 板子上跑的还是"本机回环"版本。你完全独立地对着契约开发、用 `mosquitto_pub/sub` 自测；
> 自验通过后由用户通知固件侧，我们才开始写 MQTT 客户端。这样保证**任何时刻只有一侧是变量**。

## 0. 这台设备是什么（先纠正一个容易套错的心智模型）

本项目里还有另一台 ESP32（C3 小电视），它**只显示、只被拉取、根本不接 MQTT**。
**P4 不是它的放大版**，两者的数据方向相反：

| | C3 小电视（参考项目） | **P4 控制面板（本设备）** |
|---|---|---|
| 数据方向 | Pi → 设备（下发） | **设备 → Pi 为主**（用户下指令），Pi → 设备为辅（回执） |
| 传输 | HTTP 拉取，设备不订阅 MQTT | **MQTT 双向，设备是订阅方 + 发布方** |
| 用户入口 | 手机企业微信 @ 机器人 | **P4 屏幕上的 `Hub` app** |
| 设备角色 | 显示端 | **交互端 + 主动方** |
| 谁产生内容 | Pi 侧的采集线程 | **P4 前的用户**（敲字），Pi 侧的 Agent 应答 |

链路（P4 发起）：

```
P4 的 Hub app ──MQTT publish──> broker ──> 你（OpenClaw Agent 适配器）
                                              │
                    ┌─────────────────────────┴──────────────────────────┐
                    ▼                                                    ▼
        流式回执发回 P4                                     需要时转发给其他端侧设备
        hub/chat/p4/reply                                  hub/command/<device>
```

**定位**：这**不是闲聊窗口**（纯闲聊用小智 AI 即可）。它的用途是**对 Agent 下指令、看结果**。
所以回执的第一要求是「**看得懂、知道成没成**」，不是信息密度。

## 2. 安全边界（必须遵守）

P4 是**常驻在家庭局域网里的设备**，一旦 broker 暴露到公网，任何人都能对你的 Agent 下指令。

- **broker 只监听局域网**，绝不做端口转发。
- **必须开 `password_file` + ACL**，禁止 `allow_anonymous`。
  建议每台设备一个独立账号（`p4` 一个、你自己的调试客户端一个），
  这样某个客户端出问题时可以单点吊销。
- **ACL 按主题收窄**，不要图省事给 `#`：
  - `p4` 账号：**可发布** `hub/chat/p4`、`hub/device/p4/status`、`hub/command/p4/ack`；
    **可订阅** `hub/chat/p4/reply`、`hub/command/p4`
  - Agent 适配器账号：`hub/chat/p4` 可读、`hub/chat/p4/reply` 可写；`hub/device/p4/status` 可读；
    **`hub/command/p4` 可写、`hub/command/p4/ack` 可读**（C15 步 1 起）
  - 调试账号：只读 `hub/#`（自验用，用完可以删）
  - ⚠️ **反控那两行不加，P4 就收不到命令**：MQTT 3.1.1 下订阅一个被 ACL 拒的主题，
    broker 会拒绝该订阅（mosquitto 默认还会**直接断连**）⇒ 现象是"反复重连、没有明确报错"。
    具体表现取决于你的 `acl_file` 与 mosquitto 版本，**遇到反复重连先查这两行**。
- ✅ **加密方案已定（2026-10-24）：TLS 1.2+ + 双向认证（客户端证书）**，
  端口 **8883**；1883 明文口只绑回环、局域网不可达。落地细节见文末 §10。

- ~~**加密方案由用户拍板**~~（留作背景）：
  两条路的事实摆在这里，供用户判断：
  - **局域网明文 TCP**：P4 侧零额外开销，实现最简单。前提是家里网络可信。
  - **TLS**：更安全，但 P4 是有内存预算限制的嵌入式设备。同板上 TLS 客户端实测约占
    **41.5 KB 内部 RAM**（这部分缓冲现在已配置到 PSRAM），此外还有代码体积与握手延迟。
    P4 侧能承受，但**这是"要不要花这笔钱"的取舍，不是"能不能"的问题**。
    ⚠️ 若最终选 TLS：**必须提前告诉我们**，因为证书校验方式（CA 文件放哪、要不要双向认证）
    会影响固件侧的设计；等我们写完再改是返工。

## 3. 连接参数（由 P4 发起，你只需配合）

| 项 | 值 | 备注 |
|---|---|---|
| `client_id` | `p4-<MAC 后 6 位小写 hex>`，如 `p4-a1b2c3` | 稳定不变，可用来做白名单 |
| `clean session` | `true` | **P4 不做离线消息堆积**，见 §5.4 第 3 条 |
| `keepalive` | 60 s | |
| 协议版本 | MQTT 3.1.1 | |
| QoS | **一律 1** | 不用 QoS 2 |
| 主题前缀 | `hub/` | P4 侧做成可配置项；**目前定死 `hub/`，不要自己换** |
| 设备 ID | `p4` | 主题里那段 `p4`。将来可能加别的设备，**请把 device id 做成参数，别硬编码进代码逻辑** |

**上线 / 下线**（P4 自己维护，你不用发）：

```
上线：publish hub/device/p4/status  retain=true  QoS1
      {"v":1,"online":true,"client_id":"p4-a1b2c3","fw":"c14.3","ts":1730000000}

遗嘱（LWT）：broker 在 P4 异常掉线时自动代发，retain=true
      {"v":1,"online":false,"client_id":"p4-a1b2c3"}
```

`fw` 是固件版本标签，**仅供参考，不要用它分支逻辑**。

## 4. 主题契约

| 方向 | 主题 | QoS | retain | 用途 |
|---|---|---|---|---|
| P4 → Pi | `hub/chat/p4` | 1 | **否** | 用户发出的指令 |
| Pi → P4 | `hub/chat/p4/reply` | 1 | **否** | Agent 回执（支持流式分片） |
| P4 → Pi | `hub/device/p4/status` | 1 | **是** | 在线状态 + 遗嘱 |
| Pi → P4 | `hub/command/p4` | 1 | 否 | **反控命令**（C15 步 1 起已实现，见 §11） |
| P4 → Pi | `hub/command/p4/ack` | 1 | 否 | 命令执行回执（见 §11） |
| P4 → 其他设备 | `hub/command/<target>` | 1 | 否 | 预留 |
| 其他设备 → P4 | `hub/command/<target>/ack` | 1 | 否 | 预留 |

- **`hub/chat/*` 一律不设 retained。** 设了会让 P4 一开机就重放上一条旧回复，
  用户会看到一条莫名其妙的"历史回执"。
- `hub/device/p4/status` 用 retained 是**故意的**：这样你重启后一订阅就知道 P4 在不在。

## 5. 报文契约

通用规则：

- 一律 **UTF-8 原文**，**不要用 `\uXXXX` 转义**（同样的中文，转义后字节数膨胀 ~3 倍，会撞 §5.3 的上限）。
- JSON **扁平，不要嵌套**（除了 `error` 这个对象）。P4 侧会用**定长缓冲**解析（MQTT 回调里不分配动态内存），
  嵌套越深越容易出事。
- 字段名**全小写**。
- 每条报文都带 `"v":1`。

### 5.1 P4 → Pi：用户指令

```json
{"v":1,"id":"p4-000123","ts":1730000000,"text":"把客厅的灯关掉"}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | P4 生成，**单次开机内唯一、递增**。你不会预知它的格式，**不要解析它，只回传** |
| `ts` | number | Unix 秒。P4 开机时经过 SNTP 对时，可信；**你没对时也不影响**，仅用于日志 |
| `text` | string | 用户指令原文。**中文，可能有错别字**（见 §8.1） |

### 5.2 Pi → P4：流式回执

一条回执由 **1~N 帧**组成，最后必须有一帧 `final:true`：

```json
{"v":1,"id":"p4-000123","seq":0,"delta":"好的，","final":false}
{"v":1,"id":"p4-000123","seq":1,"delta":"客厅灯已经关了。","final":true}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | **必须与请求逐字符相同**。P4 用它配对，配不上就**静默丢弃** |
| `seq` | number | 同一个 `id` 内从 **0** 开始、严格 +1。乱序或跳号不影响显示，但**影响排错**，请别乱填 |
| `delta` | string | **本帧新增的文本**（增量，不是全量）。可以为空串，用于保活 |
| `final` | bool | `true` = 这条回执结束 |

**P4 的显示行为**：发出后立刻出现一个 `...` 气泡；每收到一帧就把 `delta` **追加**到气泡里；
收到 `final:true` 才落盘为一条正式历史。所以在 `final` 之前，用户看到的是"文字在长出来"。

### 5.3 Pi → P4：错误回执

```json
{"v":1,"id":"p4-000123","seq":0,"final":true,
 "error":{"code":"agent_timeout","msg":"Agent 60 秒未响应"}}
```

- `error` 是**对象**，两个必填字段。P4 会把它显示成 `错误：<code> <msg>`。
- 一旦发 error，**必须同时 `final:true`**，并且**不要再发这个 `id` 的任何后续帧**。
- 错误码只用下面四个（新码请先问，P4 侧没有对应的处理分支）：

| code | 什么时候用 |
|---|---|
| `agent_timeout` | Agent 超时、放弃 |
| `agent_busy` | 当前忙不过来，明确拒绝（**不是**排队） |
| `bad_request` | 报文不合法：`v` 不是 1、`text` 为空、超长 |
| `internal` | 其他任何内部错误 |

### 5.4 五条硬约束（违反任何一条都会在屏幕上以"看不懂"的形式出现）

1. **单条报文 ≤ 4 KB（UTF-8 字节，不是字符数）。**
   P4 的接收缓冲规划为 8 KB，留了一倍余量；超过它的报文会被**整条丢弃**（只打一行日志），
   用户那边表现为气泡永远停在 `...`、直到超时。中文 1 字 = 3 字节，4 KB ≈ 1,300 字。
   **请在发送前自己检查字节数**，超了就在你自己的侧切片。
2. **`id` 必须原样回传。** 这是唯一能把回执和气泡对上号的东西。
3. **断连期间不排队。** P4 发失败会直接告诉用户"未发送（离线）"，**恢复后不补发**。
   你这边也不需要为它保留待投递队列 —— 参考项目那边踩过这个坑：
   断连时入队的消息会在恢复瞬间一次性推出去，变成一堆重复告警。
4. **`final:true` 恰好一次。** 一条 `id` 只能有一个终结（正常或错误二选一）。
   多发 `final` 会让 P4 把同一条内容重复落盘。
5. **QoS 1 意味着"至少一次"，可能收到重复。**
   - 你收到重复的 `hub/chat/p4`（同一个 `id`）⇒ **按 `id` 去重，不要重复执行指令**。
     建议维护最近 200 个 `id` 的环形表，带时间淘汰。
   - 你发的回复对 P4 重复一次无伤大雅（P4 会按 `seq` 累加，重复的 `delta` 会显示成重复字），
     但**请别靠 broker 去重**。

### 5.5 超时规则（两侧必须一致）

- **P4 从发出指令起计时：60 秒内没收到该 `id` 的任何一帧 ⇒ 判定超时**，
  气泡变成"超时"，并允许用户重发。
- **每收到一帧就重置这 60 秒**（任何帧都算，包括 `delta` 为空串的保活帧）。
- ⇒ 如果你的 Agent 需要想很久（比如要串几个工具、调外部 API），
  **请每 20~30 秒发一帧 `{"v":1,"id":"...","seq":N,"delta":"","final":false}` 保活**，
  否则 P4 会在 60 秒时放弃，而你之后发的帧会被丢弃（那个 `id` 已经从 P4 的在途表里删掉了）。
- 反过来：**沉默 60 秒不解释**是最糟的表现 —— 用户看到的是一个卡住的 `...`。

## 6. 内容格式（P4 的渲染限制，很容易踩）

P4 的聊天气泡是 **LVGL 的纯文本 label**，不是浏览器：

- ❌ **不要 Markdown**。`**粗体**`、`# 标题`、`- 列表`、``` 代码块``` 会**原样**显示成符号。
- ❌ **不要 emoji**。字库里没有 emoji 字形，会画成一排方框。
  （汉字、拉丁字母、阿拉伯数字、常见全角标点、`→` `·` 这类符号是有的；保险起见少用生僻符号。）
- ✅ **可以用 `\n` 换行**。
- ✅ 建议**单条回复 ≤ 300 汉字**。屏幕是 10.1" 1280×800，20 px 字，气泡宽度占列表 74%。
  要说的多就**分几帧发**（天然适合流式）。
- ❌ 不要发 base64、图片、二进制、多层嵌套 JSON —— P4 侧不会解释它们，只会把原始字串显示出来。
- 数字、单位用半角更整齐（`2.5 s` 而不是 `２．５ 秒`）。

**回执的语气建议**（这是产品定位，不是技术约束）：

- 第一句就说**成没成**："已关闭" / "没找到这个设备"。
- 失败了要给**下一步**："客厅灯没有响应，可能是离线了，要不要我重试？"
  用户没法在 P4 上自己排查，只能靠你告诉他能做什么。
- 不要复述用户的指令（屏幕上就在上面一行，重复很啰嗦）。

## 7. 自验（**在 P4 之前全部做完**，这是两侧唯一的分界线）

P4 固件现在**没有** MQTT 客户端。所以你可以完全独立地对着契约开发，用一个命令行
假扮 P4。下面这些全部通过之后，才通知用户。

### 7.1 broker 侧

```bash
# 监听地址必须是局域网，不是 127.0.0.1
ss -tlnp | grep 1883          # 期望看到 0.0.0.0:1883 或 <内网IP>:1883

# 匿名必须被拒绝
mosquitto_pub -h <Pi内网IP> -t hub/chat/p4 -m 'x'      # 期望失败/被拒

# 带账号必须成功
mosquitto_pub -h <Pi内网IP> -u p4 -P '<密码>' -t hub/chat/p4 -m 'x'
```

### 7.2 假扮 P4 发一条指令

```bash
mosquitto_pub -h <Pi内网IP> -u p4 -P '<密码>' -q 1 -t hub/chat/p4 \
  -m '{"v":1,"id":"p4-test-001","ts":1730000000,"text":"把客厅的灯关掉"}'
```

### 7.3 看回复

```bash
mosquitto_sub -h <Pi内网IP> -u observer -P '<密码>' -q 1 -t 'hub/chat/p4/reply' -v
```

期望：在 60 秒内看到若干帧，`seq` 从 0 递升，最后一帧 `final:true`，
`delta` 拼起来是一句通顺的中文，且**逐字符回传了 `"id":"p4-test-001"`**。

再用同一句重发一次（**故意重复 `id`**）⇒ 期望：**指令不会被执行两次**（你的去重生效）。

### 7.4 边界与错误路径

| 场景 | 期望 |
|---|---|
| `text` 为空串 | 回 `bad_request` + `final:true` |
| 报文 `v` 是 2 | 回 `bad_request` + `final:true` |
| 让 Agent 故意慢 90 秒 | 期间每 20~30 s 有保活帧，最终正常 `final`（而不是静默） |
| Agent 抛异常 | 回 `internal` + `final:true`，**进程不崩** |
| 单帧超过 4 KB | **你侧就不该发出这么长的帧** —— 自测一下切片是否正确 |

### 7.5 一个能看全局的窗口

```bash
mosquitto_sub -h <Pi内网IP> -u observer -P '<密码>' -t 'hub/#' -v
```

后来 P4 真接上时，用同一条命令就能看到两边的完整对话 —— 联调时很有用。

## 9. 明确不做 / 容易踩错

**P4 侧 v1 不做**（所以你不必准备）：

- ❌ 语音输入（端侧没有 ASR，用户只能手打）
- ❌ 图片/文件消息
- ❌ 多会话 / 会话切换（只有一条对话流）
- ❌ 消息撤回
- ❌ 离线消息补发
- ~~❌ 反控 `hub/command/p4`（主题先占着，**格式未定，别先用**）~~
  ✅ **2026-10-28（C15 步 1）起已实现**，但只有**两条固定命令**：`music` / `aichat`，
  格式见 §11。**没有**通用的"打开任意 app / 点任意按钮"能力。

**最容易踩的六个**：

1. **把 P4 当浏览器。** Markdown/emoji 都会原样显示。§6 是硬限制。
2. **以为 P4 会补发。** 断连就是失败，用户会看到"未发送（离线）"。
3. **沉默超过 60 秒。** 必须保活，或者干脆早点回错误。
4. **`final:true` 发两次。** P4 会落盘两条重复历史。
5. **报文超 4 KB。** 超过的被整条丢弃，用户只看到卡住的 `...`，没有任何错误提示。
6. **把 `id` 当字符串解析。** 它不是 UUID，也不是时间戳，只是个不透明的配对键。

**另外两条和内容相关的**：

- **P4 的输入能力有限**：拼音只能逐字选（没有词组联想），所以用户很可能打出
  "把客厅的等关调" 这种错字。**请对错别字宽容**，必要时反问确认，
  而不是直接报"没有这个设备"。
- **用户不知道你在干什么**：树莓派的日志他看不到。要让他知道"在做了"，
  唯一的手段就是发帧。**沉默 = 卡死**，在他眼里两者没有区别。

## 11. 反控命令（C15 步 1，2026-10-28 起可用）

> 定位：**验证 P4 能被 Pi 侧驱动**，不是"通用远程控制"。
> 设备侧实现见 `components/brookesia_hub_commands/`。

### 11.1 两条固定命令

Pi → P4：`hub/command/p4`，QoS 1，**不要 retained**。

```json
{"v":1,"id":"pi-0001","cmd":"music"}                  # 打开 + 播第 1 首
{"v":1,"id":"pi-0002","cmd":"music","arg":"open"}     # 只打开，不出声
{"v":1,"id":"pi-0003","cmd":"music","arg":"close"}    # 关掉，回桌面（音乐停）
{"v":1,"id":"pi-0004","cmd":"aichat"}                 # 打开小智
{"v":1,"id":"pi-0005","cmd":"aichat","arg":"close"}   # 关掉小智，回桌面
{"v":1,"id":"pi-0006","cmd":"close_all"}              # 一键清理所有后台
```

| `cmd` | 正向 | 反向 |
|---|---|---|
| `music` | 省略 / `arg:"play"` = 打开**并播第 1 首**；`arg:"open"` = 只打开不出声 | `arg:"close"`（或 `"stop"`）= **关掉回桌面，音乐停** |
| `aichat` | 省略 / `arg:"open"` = 打开小智，会话由它自己准备 | `arg:"close"`（或 `"stop"`）= **关掉回桌面，会话结束** |
| **`close_all`** | 无（`arg` 必须省略） | **把所有正在运行的 app 全部关掉**，屏幕回桌面 |

**`close_all` = 最近任务里那个垃圾桶**，逐个 app 发同一条 `STOP` 事件；
效果是"一键释放后台"：音乐停、小智会话断、相机/相册/视频等一并退出。
它**不受**当前有没有前台 app 影响（前台开着也照样清掉），并且**幂等**：
没有 app 在跑时回 `ok:true` + `"closed":0`。

**`close` 的确切语义 = 最近任务里点那个垃圾桶**。它走的是框架同一条 `STOP` 事件
（`esp_brookesia_phone_manager.cpp:1207-1222` → `App::processClose()` →
`MusicPlayer::close()` 里的 `audio_player_pause()` + `bsp_extra_player_del()`）⇒
**即使音乐在后台放着，也会真停**，不是"只把界面关掉"。

⚠️ `close` 是**幂等**的：app 本来就没在运行 ⇒ 回 `ok:true`，不报错。

- `id` **建议必带**：ack 原样回传，没有它就无法配对。
- 未知 `cmd` ⇒ 回 `unknown_cmd`，**不做任何事**（不会去开别的 app）。
- **同一 `id` 重复投递不去重**：两条命令本身幂等（app 已开着就 resume），
  重复最多是"又从头播了一遍第 1 首"。要准就别重发。

### 11.2 ack

P4 → Pi：`hub/command/p4/ack`，QoS 1，不 retained。

```json
{"v":1,"id":"pi-0001","cmd":"music","ok":true}
{"v":1,"id":"pi-0003","cmd":"aichat","ok":false,"error":"not_installed"}
{"v":1,"id":"pi-0006","cmd":"close_all","ok":true,"closed":3}
```

`closed` 字段**只有 `close_all` 会带**（这一下清掉了几个 app）；其余命令不带。

| `error` | 含义 |
|---|---|
| `unknown_cmd` | 不是 `music` / `aichat` |
| `bad_arg` | `arg` 不认识（只支持 `play` / `open` / `close`，`stop` 是 `close` 的别名） |
| `not_installed` | 桌面上找不到该 app（名字被改了？） |
| `event_failed` | 给框架发 START / STOP 事件失败 |
| `start_failed` | 事件发出去了，但 app 没进运行表（真启动失败） |
| `close_failed` | 事件发出去了，但 app 还在运行表里（真关闭失败；`close_all` 只要还剩一个就报这个） |
| `no_track` | MusicPlayer 开了，但一首歌都没扫到 |
| `busy` | 命令队列满（Pi 连发太快） |

⚠️ **`ok:true` = "命令已执行到位"**（app 已打开、播放请求已发出），**不是"正在出声"**。
播放是异步的；真失败时 P4 串口会打 `Failed to start track`。

⚠️ **断连期间不排队**（与聊天同一条契约）：没连上就收不到，连上后也**不会补执行**。

### 11.3 验收

用一个**有发布权限**的凭据（Agent 适配器那套），或直接让 OpenClaw 发：

```bash
mosquitto_pub -h <Pi> -p 8883 --cafile ca.crt --cert <agent>.crt --key <agent>.key -q 1 \
  -t hub/command/p4 -m '{"v":1,"id":"t1","cmd":"music"}'

mosquitto_sub -h <Pi> -p 8883 --cafile ca.crt --cert <agent>.crt --key <agent>.key -q 1 \
  -t hub/command/p4/ack -v
```

**判据**：发完 `music` 后 P4 屏幕**自己**切到音乐页并开始响，同时收到 `ok:true`。
`aichat` 同理（屏幕切到小智）。

**反向也要验**（2026-10-28 补）：

```bash
# 先让音乐在后台放着（上滑回桌面），再发这条 ⇒ 声音必须停
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t3","cmd":"music","arg":"close"}'
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t4","cmd":"aichat","arg":"close"}'
# 再开两三个 app，然后一键清（回执里看 closed 等于几个）
mosquitto_pub ... -t hub/command/p4 -m '{"v":1,"id":"t5","cmd":"close_all"}'
```

**判据**：`music close` 之后**后台也听不到声音了**（不是"界面关掉但还在放"）；
再发一次同一条命令也应回 `ok:true`（幂等）。

### 11.4 已知边界

- **只有这两条**：没有"打开任意 app / 点任意按钮 / 调音量"。
- **music 与 aichat 别同时用**：MusicPlayer 进后台**故意不断音频**（`MusicPlayer.cpp:277`），
  两路会同时抢同一个 ES8311 / I2S 通路。**分开测**。
- 运行中的 app 上限是 **3**；开满后再开新的，框架会关掉一个 —— 关的是它内部表顺序里的
  "最后一个"，**不保证最老**。所以别在满 3 个时指望 MusicPlayer 还在放。
- 时延：命令是 QoS1 到达 + 100 ms 轮询，正常 **< 0.5 s**，但**没有实测数据**（还没跑过）。
