# win-agent · 指令源侧客户端

**让「另一个接入方」也能安全地指挥端侧设备 —— 而不只是 Pi 上那个 Agent。**

本仓原本的控制路径是「Pi 侧的机器人 → broker → 设备」。本目录演示的是**第二条路径**：
**任何持有独立凭据的接入方** —— 另一台电脑上的 Agent、另一个服务、你自己的脚本 ——
都能接进总线、驱动端侧设备，**而权限是收窄的**。

> 这套设计的重点不是"能连上"，而是 **"连上之后只做得了被允许的那几件事"**。
> 安全不来自彼此信任，来自 broker 上的三件东西：
> **一套独立证书 · 一个独立 ACL 角色 · 一段按主题收窄的授权**。
> 任何一环缺失，这条路径都不成立。

[`p4-agent/`](../p4-agent/) 是**设备侧**的样本（订阅命令 → 调设备 → 回结果）；
本目录是**指令源侧**的对称物（发命令 → 等配对回执）。两者合起来，
才是一条完整的 `Agent → broker → 设备 → 回执` 闭环。

> ⚠️ **P4 面板与小车只是这套闭环的最小示范，不是这个设计的边界。**
> 任何订阅 `hub/command/<设备>` 的端侧设备都能接进来 ——
> 设备侧照 [`p4-agent/`](../p4-agent/) 写一个适配器，
> 接入方这边改一张指令表（见 [接入你自己的设备](#接入你自己的设备)）。
> 本目录**刻意不为"某台具体设备"设限**：协议层是通用的，定制只在两端各一张表。

## 反控的安全模型

一条指令从"另一个接入方"走到设备，要过四道关。**每一道都在 broker 上，不在客户端的自觉里**：

| 关卡 | 做了什么 | 效果 |
|---|---|---|
| 传输 | mTLS：TLS 1.2+、双向证书、校验主机名 | 没有证书连不上 `8883`；证书 SAN 与 IP 不符就断 |
| 身份 | 每个接入方**一套账号 + 一套证书** | 一台接入方被攻破，不影响其他接入方 |
| 授权 | ACL **逐主题**授权，绝不给 `#` | 只能写它该指挥的设备、读那些设备的回执 |
| 兜底 | 越权读写由 broker 静默丢弃 | 实测 8 个用例（含 3 个通配）**0 泄漏** |

**这个模型的意义**：能力边界由 **broker 的授权表**决定，不由接入方的自我约束决定。
想给某台设备再加一个控制方，就加一段 ACL；想收回，改一行 —— 不用去那台设备上动任何东西。
**设备侧一个入站端口都不用开**，它只是往 broker 发/收消息。

> 📌 这也解释了为什么本仓坚持「**每台设备独立凭据 + 独立 ACL 角色**」：
> 一份凭据能碰多少东西，决定了一次泄露的爆炸半径。

## 快速开始

```bash
cd win-agent
python -m venv .venv
.venv/bin/pip install -r requirements.txt        # Windows: .venv\Scripts\pip

cp .env.example .env                             # 填 host / user / password，放好三张证书

python -m winagent doctor                        # 自检：TLS + 建连 + 一条不动机器的命令
python -m winagent list                          # 看设备与指令表
python -m winagent car help                      # 连通性自检（不动机器）
```

典型输出：

```
① TLS
   版本   : TLSv1.3
   套件   : TLS_AES_256_GCM_SHA384
   SAN    : DNS:pihub.local, IP Address:127.0.0.1, IP Address:192.168.1.100
   主机名 : ✓ 证书覆盖 192.168.1.100

② 命令往返（car/help —— 不动机器）
   ✓ 77 ms
```

## 配置

| 键 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `WIN_MQTT_HOST` | ✅ | — | broker 地址 |
| `WIN_MQTT_USER` | ✅ | — | 账号名 |
| `WIN_MQTT_PASSWORD` | ✅ | — | 密码 |
| `WIN_MQTT_PORT` | | `8883` | TLS 端口 |
| `WIN_MQTT_CA` | | `ca.crt` | CA 证书 |
| `WIN_MQTT_CERT` | | `<user>.crt` | 客户端证书 |
| `WIN_MQTT_KEY` | | `<user>.key` | 客户端私钥 |

- **查找顺序**：`--env PATH` → 环境变量 `WINAGENT_ENV` → 当前目录的 `.env`
- 证书类相对路径**按 .env 所在目录解析**，整套凭据可以整体搬走
- 🔴 `.env` / `*.crt` / `*.key` **一律不进 git**；建议放在仓库之外并设为仅本用户可读
- 主机名校验是**开着**的：broker 证书 SAN 里带着它的 IP，**IP 变了就该连接失败**
  —— 那是提示去重签证书，不是绕开的障碍

## 命令

```bash
python -m winagent <设备> <指令> [参数]
```

| 设备 | 指令 | 说明 | 实测回执耗时 |
|---|---|---|---|
| `p4` | `music` [`play`/`open`/`close`/`stop`] | 打开并播放 / 只打开 / 关闭 | 0.36 s |
| `p4` | `aichat` [`open`/`close`/`stop`] | 打开小智 / 关闭 | — |
| `p4` | `close_all` | 关闭全部后台（幂等） | — |
| `car` | `help` | 返回指令表（**不动机器**） | 0.08 s |
| `car` | `spin` | 原地转一圈 | 2.4 s |
| `car` | `showoff` | 露一手：转 3 圈 + 播 EG 音乐 | **22.0 s** |
| `car` | `music` | 播放歌库 | 0.09 s |
| `car` | `stop` | 停止 / 急停 | 0.13 s |

> 🔴 **默认超时按指令给，不是一个全局值。** 因为 `showoff` 的 ack 要等整段动作跑完
> 才回来（22 秒），用 8 秒会必然超时 —— 而且报出来是"设备没回"，**分类就错了**。
> 要改就用 `--timeout` 显式覆盖。

常用开关：

| 开关 | 作用 |
|---|---|
| `--json` | 机器可读输出（供 Agent 解析） |
| `--timeout 8` | 等回执的秒数（不含建连；建连固定 8 s）。不写则按指令取默认值 |
| `--wait-final` | **预留**：若有中间回执则继续等终态。当前车侧只回一条终态 ack，等于没作用 |
| `--final-timeout 40` | `--wait-final` 的总预算 |
| `--id XXX` | 自定义命令 id（默认自动生成） |

> ⚠️ 指令名写错**不会被本地拦下**：程序只在 stderr 提醒，命令照样发出去，
> 由设备回 `unknown_cmd`。这是一次**诚实的往返**，比客户端偷偷过滤更有诊断价值。

## 输出与退出码

| 码 | stage | 含义 |
|---|---|---|
| `0` | `ok` | 收到 ack 且 `ok:true` |
| `2` | `config` | 本地配置 / 证书缺失 |
| `3` | `tls` | 握手失败（证书过期、CA 不对、SAN 不含该 IP） |
| `4` | `connect` | TCP 或 CONNACK 失败（凭据错误、broker 没开） |
| `5` | `subscribe` | 订阅 ack 主题没拿到 SUBACK |
| `6` | `timeout` | 发出去了但超时没有 id 配对 |
| `7` | `device` | 设备回了 ack，但 `ok:false` |

失败时一定同时给出 `stage` + 人话原因，**不会把超时写成成功**。

## 五条实装约束（每条都有实测依据）

1. **先订阅、拿到 SUBACK 才发。**
   不是在订阅后 `sleep(1.2)` 猜——`on_subscribe` 回调里拿到 SUBACK 才继续。
   没有订阅者时 broker **根本不投递**，表现是"超时"，而设备其实已经动了。

2. **用 `id` 配对，不认"收到任何 ack"。**
   总线上可能同时有别人的回执；id 对不上的一律丢弃。

3. **不自动重试。**
   设备侧**不按 `id` 去重**（`p4-agent` 的命令路径只做入队 → 执行），
   重复投递 = 重复执行。`close_all` 幂等无碍，`music` / `aichat` 会再开一次。
   ⇒ 本客户端**没有任何重试逻辑**，失败就如实返回。

4. **PUBACK 和 SUBACK 都不可信。**
   ACL 拒绝时 broker 两者都照常回成功，只在投递时静默过滤。
   判断"到底有没有权限"的唯一办法是**实际收到哪些主题**。

5. **两台设备的应答模型不同，别"统一"掉 —— 而且别照抄"受理 + done"那个说法。**
   - `p4`：**一次性同步回执**，收到即终态（`music` 实测 0.36 s）。
   - `car`：**MQTT 上同样只有一条 ack**，但**耗时等于动作时长**：
     `spin` 2.4 s、`showoff` **22.0 s**、`music` 0.09 s。
     ⇒ **超时必须按指令给**，一个全局 8 秒会让 `showoff` 永远超时。

   ⚠️ **"先回『已受理』、动作结束再补 `done`"说的是 `app/car_bot.py` 发给企微的那条消息**，
   **不是总线上的 ack**。2026-11-03 用 `spin` / `showoff` 实测：两条长指令都只收到
   **1 条** ack，中途一条都没有。
   ⇒ **别把"给人看的受理文案"当成"MQTT 协议行为"** —— 这两层只差一层，很容易混。
   本客户端因此默认"收到 ack 就是终态"，`--wait-final` 只是给将来的中间回执留的开关。

   📌 `status:"done"` 的含义也不统一：`music` 的 `done` 是"开始播放"（0.09 s 就回），
   `showoff` 的 `done` 才是"整段动作跑完"（22 s）。**别拿 `done` 当"物理动作已完成"的证据。**

## 接入你自己的设备

**本目录的 P4 与小车只是示例**，不是你必须拥有的设备。换成你自己的，只要动两端各一张表：

| 端 | 改什么 | 在哪 |
|---|---|---|
| 设备侧 | 写一个同构适配器：订阅 `hub/command/<你的设备>`、执行、回 `<设备>/ack` | 照 [`p4-agent/`](../p4-agent/) 抄 |
| 授权侧 | 给设备一个 ACL 角色、给每个接入方一个只含那几行的角色 | [`config/aclfile.example`](../config/aclfile.example) |
| 客户端 | 在指令表里加一条：`设备名 → 主题 / 指令 / 默认超时` | [`winagent/__main__.py`](winagent/__main__.py) 的 `DEVICES` |

**协议层不用改。** 报文始终是 `{v, id, cmd, arg?}`，回执按 `id` 配对；
变的只是"这台设备认哪些 `cmd`"和"它多久能回"。
这正是本仓「**通用的是怎么管，不是怎么接**」那句话的具体形态 ——
设备各式各样，接入方式各自定制，而**授权模型是共用的**。

> 需要提醒的一句：指令集是**设备专属**的。给小车发 `spin`、给面板发 `music`，
> 换个设备就得重写解析。别指望一套指令名打天下 —— 那只会得到一个谁都不认的中间层。

## 边界（写清楚，免得误用）

| 它能做 | 它不能做 |
|---|---|
| 发指令、拿配对回执 | ❌ **读设备状态**（ACL 不给 `hub/device/*`） |
| 知道命令"被设备处理了" | ❌ 知道"设备在线吗" —— 离线与被丢弃都表现为 `timeout` |
| 每次一条独立连接（≈80 ms） | ❌ 后台常驻、断线自动补发 |
| 与既有的企微 / Pi 侧链路并存 | ❌ 与它们互斥 —— 两个来源同时写同一台设备时没有仲裁 |

> **没有 `src` 字段**：报文仍是 `{v, id, cmd, arg?}`，设备端分不出是谁发的。
> 这是当前契约的已知缺口，加字段需要设备侧一起改，不在本客户端单方面添加。
